## Problem Statement

chantierMobile (Django construction-site management SaaS, DRC/Great Lakes region) is pre-product — no paying customers yet, recent commits are QA/i18n bug fixes. A competitor product, Axxe Digital's "Suivi Budgétaire Chantier Personnel" (a $6 one-time Excel template, 216+ sales, seller has 21,827 total customers), sells budget-per-phase tracking, material stock alerts, and budget-threshold alerts to the same DRC/Francophone-Africa construction audience. Comparing against the actual chantierMobile codebase surfaced two real schema gaps: `Budget` is `OneToOne` with `Site` only (no per-phase breakdown), and `Material` has no on-hand quantity field at all (no stock accounting, just a request/order workflow). No alert or notification system exists anywhere in the running app — only aspirational test comments describing what "would" happen "in a real implementation."

## Demand Evidence

Initial evidence offered was weak: "inferred from Axxe's traction" — a $6 one-time Excel purchase by a solo DIY home-builder is a different buying decision than an existing (or soon-to-be-paying) chantierMobile director adopting a new SaaS module, and doesn't by itself prove chantierMobile's own users are blocked. Pushed twice. Stronger answer that emerged: a chief/site engineer using the pre-launch app has informally said something like "I don't know we're low on materials until it's too late." Not a named individual with a dated incident, but a role-level signal from actual usage, not a hypothetical.

## Status Quo

The chief/site engineer currently tracks material stock and budget burn via a manual paper notebook, completely disconnected from the chantierMobile app — a classic duct-taped workaround, and the same tool category (pen-and-paper / spreadsheet) Axxe's own product targets.

## Target User & Narrowest Wedge

**Target user:** the chief/site engineer (CHIEF_ENGINEER / ENGINEER roles) — not the director, who the earlier (unbuilt) 2026-05-15 notification design actually targeted. That was a role mismatch: the validated pain is the engineer getting **blamed by the director** for an overrun or shortage they didn't see coming — an accountability/trust hit, not a mere inconvenience.

**Revised during session:** routing the alert to the engineer alone doesn't remove that blame exposure — it just delays it. If the director later asks "why didn't you tell me," an engineer-only alert is no defense. The fix isn't picking a recipient, it's **removing the asymmetry**: both roles see the identical page, identical badges, at the same time. Nobody is "informed first," so nobody can claim they weren't told.

**Narrowest wedge:** color-coded phase-budget and material-stock status, computed synchronously on page load (no push infra), added to the existing site-detail page, visible identically to engineer and director roles.

## Constraints

- Pre-product stage — no paying customers to validate against yet; this is a bet, not a response to a support queue.
- Railway + Supabase PgBouncer (`CONN_MAX_AGE=0`) + Django Channels/Daphne compatibility is explicitly unvalidated per TODOS.md, and deliberately gated behind reaching "5 paying directors × 30 days" — i.e., real-time push infra is out of scope until well past this feature's launch.
- Users are mobile-first on the DRC/Goma market, plausibly intermittent connectivity — anything requiring a persistent connection (WebSockets) is a reliability risk, not just an infra-validation risk.
- Existing visual language is Bootstrap 5: white `border-0 shadow-sm` cards, `rounded-pill` badges colored by a `bg-success`/`bg-warning`/`bg-danger` threshold triad already driving the site-level budget badge (`site_detail.html:534`, >80% red, 60-80% amber, <60% green).

## Premises

1. The validated pain point is the chief/site engineer's blame exposure when an overrun/shortage happens — not the director, who the prior (unbuilt) notification design actually targeted. **Revised in session:** the fix is symmetric visibility (both roles see the same page), not just re-routing the recipient — an engineer-only alert with no escalation/shared-visibility path still leaves the engineer exposed.
2. The alert LOGIC (80% budget threshold, per-phase granularity, low-stock reorder threshold) is low-risk and industry-validated — confirmed via landscape search (construction cost-tracking and inventory tools treat both as baseline/conventional, not novel bets).
3. The DELIVERY mechanism in the prior design (Django Channels + WebSocket real-time push) is unvalidated infrastructure risk for a pre-product app, and is separable from the alert logic — the logic can ship without that specific delivery mechanism.
4. Per-phase budgets and material stock quantities are both real, verified schema gaps today — confirmed by reading `finance/models.py` (`Budget` is Site-only) and `materials/models.py` (`Material` has no quantity field).

## Approaches Considered

### Approach A: Computed badges, shared visibility — SELECTED
Effort: S/M (human ~3-4 days / CC ~1 hr). Risk: Low. Add `PhaseBudget`, `Expense.phase` FK, a per-site stock model, and a movement log (see Schema below). Extend the existing `budget_usage_percentage` computed-property pattern to `ProjectPhase`. Render as color-coded badges on the site-detail dashboard, visible to both engineer and director roles from day one — no notification model, no read/unread state, no escalation timer, because nobody is ever hidden from it. Reuses `Site.total_spent`-style computed properties directly, zero new infra.

#### Schema (field-level, post-review)

```python
# finance/models.py additions
class PhaseBudget(BaseModel):
    phase = models.OneToOneField('projects.ProjectPhase', on_delete=models.CASCADE, related_name='budget')
    allocated_amount = models.DecimalField(max_digits=14, decimal_places=2)  # matches Budget.total_amount precision

    def clean(self):
        # A PhaseBudget cannot exist without a site-level Budget to allocate
        # from — closes the round-2-flagged loophole where a phase could get
        # a budget before (or independent of) the site ever having one.
        site = self.phase.site
        if not hasattr(site, 'budget'):
            raise ValidationError('Site must have a Budget before any phase can be allocated one.')
        other_allocations = PhaseBudget.objects.filter(
            phase__site=site
        ).exclude(pk=self.pk).aggregate(total=models.Sum('allocated_amount'))['total'] or 0
        if other_allocations + self.allocated_amount > site.budget.total_amount:
            raise ValidationError('Sum of phase allocations cannot exceed the site budget total.')
        # Note: this constrains the ALLOCATION pool, not actual spend — a
        # single phase can still legitimately show red (over its own
        # allocation) while the site shows green (other phases underspent).
        # That's correct behavior, not a bug this check prevents.

# Budget gets a symmetric check so the reverse direction (lowering
# total_amount below what's already allocated to phases) is caught too —
# round 2 flagged the original check as one-directional.
class Budget(BaseModel):
    # ... existing fields unchanged ...
    def clean(self):
        if self.pk:
            allocated = PhaseBudget.objects.filter(
                phase__site=self.site
            ).aggregate(total=models.Sum('allocated_amount'))['total'] or 0
            if allocated > self.total_amount:
                raise ValidationError(
                    f'Cannot reduce budget below {allocated}, the sum already allocated to phases.'
                )

# Expense gets one new nullable field:
class Expense(BaseModel):
    # ... existing fields unchanged ...
    phase = models.ForeignKey('projects.ProjectPhase', on_delete=models.SET_NULL, null=True, blank=True, related_name='expenses')

    def clean(self):
        # ... existing validation unchanged ...
        # Round-2 fix: a phase belonging to a different site than the expense
        # would silently corrupt phase-level spend aggregation with another
        # site's money — the exact invariant PhaseBudget.clean() is meant to
        # protect, so this has to be checked here too.
        if self.phase_id and self.phase.site_id != self.site_id:
            raise ValidationError({'phase': 'Phase must belong to the same site as the expense.'})
    # Existing expenses keep phase=NULL. NULL-phase expenses still count toward
    # Site.total_spent (unchanged) but are excluded from any PhaseBudget's spend
    # total — this is a known, accepted v1 gap: phase-level tracking is only as
    # complete as the engineer's phase-tagging habit going forward, not
    # retroactive. State this to the user in the UI (e.g. "N untagged expenses
    # not shown in phase breakdown") rather than silently under-reporting.
```

```python
# materials/models.py additions — per-site, not per-Material (Material has no
# Cabinet/Site FK; it's a shared global catalog referenced across every
# cabinet's MaterialRequestItem rows, so stock fields cannot live there
# without leaking one cabinet's depletion into another's dashboard).
class SiteMaterialStock(BaseModel):
    site = models.ForeignKey('projects.Site', on_delete=models.CASCADE, related_name='material_stock')
    material = models.ForeignKey(Material, on_delete=models.PROTECT, related_name='site_stock')
    quantity_on_hand = models.DecimalField(max_digits=10, decimal_places=2, default=0)
    reorder_threshold = models.DecimalField(max_digits=10, decimal_places=2)
    # Status tiers (round-2 fix: spelled out explicitly, not left implicit):
    #   RUPTURE if quantity_on_hand <= 0
    #   BAS     if 0 < quantity_on_hand <= reorder_threshold
    #   OK      if quantity_on_hand > reorder_threshold
    # Threshold comparison, not a percentage — there's no natural "100%" for
    # a stock count the way there is for a budget, so this deliberately does
    # NOT reuse the budget badge's >80/60-80/<60 percentage triad.

    class Meta:
        unique_together = ('site', 'material')

    def clean(self):
        # Round-3 fix: a threshold of 0 (or negative) makes BAS unreachable —
        # the material jumps straight from OK to RUPTURE with no warning
        # window, silently defeating the feature's whole early-warning
        # purpose without ever raising an error. Same positivity pattern as
        # Expense.amount / MaterialRequestItem.quantity elsewhere in this repo.
        if self.reorder_threshold <= 0:
            raise ValidationError({'reorder_threshold': 'Reorder threshold must be a positive number.'})

class StockMovement(BaseModel):
    class MovementType(models.TextChoices):
        RECEIVED = 'received', _('Reçu')
        CONSUMED = 'consumed', _('Consommé')

    stock = models.ForeignKey(SiteMaterialStock, on_delete=models.CASCADE, related_name='movements')
    movement_type = models.CharField(max_length=20, choices=MovementType.choices)
    quantity = models.DecimalField(max_digits=10, decimal_places=2)
    recorded_by = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.SET_NULL, null=True)
    note = models.TextField(blank=True)

    def clean(self):
        # Round-2 fix: neither positivity nor over-consumption was checked in
        # the prior revision, unlike every comparable model in this repo
        # (Expense.amount, MaterialRequestItem.quantity, Budget overspend).
        if self.quantity <= 0:
            raise ValidationError({'quantity': 'Quantity must be a positive number.'})
        if self.movement_type == self.MovementType.CONSUMED and self.quantity > self.stock.quantity_on_hand:
            raise ValidationError({'quantity': f'Cannot consume more than the {self.stock.quantity_on_hand} on hand.'})
    # BOTH movement types are created the same way — through the one manual
    # "Record a movement" form described below. Round-2 review found that the
    # prior revision's "RECEIVED auto-created on MaterialRequest DELIVERED"
    # depends on a status transition that doesn't exist anywhere in the app
    # today (approve_material_request only handles approve/reject; DELIVERED
    # is rendered in templates but nothing ever sets it). Rather than scope
    # in building that whole lifecycle as a prerequisite, RECEIVED movements
    # are manually recorded too — same form, different movement_type. Wiring
    # this to an eventual MaterialRequest delivery-confirmation feature is a
    # natural future integration, explicitly out of scope here.
```

**Recording a movement (post-review fix — the original design only had inbound movements inferred from an unbuilt transition, so `quantity_on_hand` could only ever increase and a "low stock" badge would never fire meaningfully).** One small form on the site-detail page, available to CHIEF_ENGINEER/ENGINEER roles: material, movement type (Reçu/Consommé), quantity, optional note — the same day-to-day action as writing a line in the paper notebook it's replacing. If no `SiteMaterialStock` row exists yet for that site+material, the same form asks for an initial `reorder_threshold` to create one (closes the round-2-flagged gap where the threshold field had no default and no way to get set). This is manual entry, not automatic sensing — consistent with "narrowest wedge," and it directly maps to the validated status quo.

**Concurrency (round-3 fix).** The view handling this form must wrap the read-check-write in `transaction.atomic()` with `SiteMaterialStock.objects.select_for_update()` before running `StockMovement.clean()`'s over-consumption check and updating `quantity_on_hand` — otherwise two people recording a CONSUMED movement against the same stock row concurrently (plausible: multiple people near the same materials store) can each read the same pre-update quantity, both pass validation, and together drive it negative. This exact race-condition class was already hit and fixed once in this codebase (`Expense.approve()` locks the `Budget` row for the same reason — see `finance/models.py`); reuse that pattern here rather than re-deriving it. The same applies to `PhaseBudget`/`Budget` reconciliation writes, at lower likelihood given directors approve budgets less frequently than engineers log material usage.

**RBAC note:** `SiteDetailView` currently has no `RoleRequiredMixin` (confirmed in `projects/views.py`), so WORKER/CASHIER roles can also reach this page today. The new phase-budget/stock section is not restricted further — visible to anyone who can already view site-detail, consistent with "symmetric visibility, no conditional rendering." If that turns out to be too broad, that's a follow-up RBAC change to the view, not to this feature.

**i18n:** all new UI strings (badge labels, table headers, the movement-recording form) go through the existing `gettext_lazy` pipeline per repo convention — same as every other user-facing string in the app.

**Test plan:** unit tests for `PhaseBudget.clean()` (allocation-sum validation, both directions — creating a phase allocation over budget, and reducing a budget below existing allocations), `Expense.clean()`'s phase/site cross-check, `ProjectPhase.budget_usage_percentage` edge cases (no `PhaseBudget` yet → 0, zero allocated, over 100%), `StockMovement.clean()`'s positivity and over-consumption checks, `SiteMaterialStock.clean()`'s reorder-threshold positivity check, and a template-rendering test confirming both DIRECTOR and CHIEF_ENGINEER role fixtures see identical badge output — consistent with `pytest.ini`'s 80% coverage floor. **Explicitly included per round-2 review:** a cross-cabinet isolation test — two sites in different cabinets holding stock for the same `Material` must never see each other's `quantity_on_hand`. **Explicitly included per round-3 review:** a concurrency test — two simultaneous CONSUMED movements against the same `SiteMaterialStock` row must not be able to drive `quantity_on_hand` negative (proves the `select_for_update()` locking actually holds, not just that `clean()` rejects a single over-consumption request in isolation).

### Approach B: Full Notification model + escalation, no push — rejected for v1
Effort: L (human ~1-2 weeks / CC ~3-4 hrs). Risk: Medium. Would build the already-specced `Notification` model (from the 2026-05-15 doc) with signals in `finance`/`materials`, rendered via a polled partial instead of WebSocket push, plus a Celery escalation task. Rejected for v1 as the heaviest pre-product bet of the three — a durable audit trail and reusable notification infra are real value, but not worth the cost before Approach A validates that anyone actually looks at the dashboard at all.

### Approach C: Daily digest (email/log), no in-app UI — rejected for v1
Effort: S (human ~2 days / CC ~40 min). Risk: Low. A daily Celery task (reusing `mark_overdue_invoices`) emailing a phase-budget/stock summary to both roles simultaneously — matches the validated status quo (these users aren't opening the app daily yet) better than an in-app badge nobody remembers to check. Rejected for v1 only because it was a close second, not because it's wrong — worth revisiting as a fast-follow if Approach A's in-app badges turn out to go unseen (see Open Questions).

## Recommended Approach

**Approach A.** Cheapest to ship, zero new infrastructure, and satisfies the revised premise (symmetric visibility) by construction rather than by adding state-tracking machinery. It's also the correct order of operations for a pre-product bet: validate that the dashboard gets looked at before investing in Approach B's audit trail or Approach C's digest delivery.

## Success Criteria

- `PhaseBudget`, `SiteMaterialStock`, and `StockMovement` exist with migrations, inheriting `BaseModel` per repo convention; `Expense.phase` is a plain nullable FK added to the existing model.
- `PhaseBudget.clean()` enforces a site's phase allocations never exceed its `Budget.total_amount`, requires a `Budget` to exist first, and `Budget.clean()` symmetrically blocks reducing `total_amount` below what's already allocated.
- `Expense.clean()` rejects an expense whose `phase` belongs to a different site than the expense itself.
- `ProjectPhase` gains a `budget_usage_percentage`-equivalent computed property (returns 0 with no `PhaseBudget` yet), following the exact pattern already used by `Site.budget_usage_percentage`.
- `SiteMaterialStock.quantity_on_hand` moves only via `StockMovement` rows, both RECEIVED and CONSUMED created through the same manual "Record a movement" form — never edited directly. `StockMovement.clean()` rejects non-positive quantities and CONSUMED entries exceeding what's on hand; the recording view wraps this in `transaction.atomic()` + `select_for_update()` (mirroring `Expense.approve()`'s existing budget-locking pattern) so concurrent submissions can't race `quantity_on_hand` negative. `SiteMaterialStock.clean()` rejects a non-positive `reorder_threshold`.
- Site-detail page renders per-phase budget badges and a per-site material-stock table (columns: Matériau, Sur site, Seuil, Statut, Dernier mouvement; status tiers RUPTURE/BAS/OK per the threshold rule in the Schema) identically regardless of whether the viewer holds the DIRECTOR, CHIEF_ENGINEER, ENGINEER, WORKER, or CASHIER role — no conditional rendering by role for this section.
- RUPTURE/low-stock rows sort to the top via the view's queryset ordering (severity-then-name), not client-side JS.
- All new user-facing strings (badges, table headers, the movement-recording form) go through `gettext_lazy`, matching every other string in the app.
- Test coverage (consistent with `pytest.ini`'s 80% floor) includes: `PhaseBudget`/`Budget` reconciliation in both directions, the `Expense` phase/site cross-check, phase `budget_usage_percentage` edge cases, `StockMovement` positivity/over-consumption checks, a role-parity template-rendering test, and a cross-cabinet stock-isolation test (two sites in different cabinets, same `Material`, never see each other's `quantity_on_hand`).
- Zero new infrastructure dependencies (no Channels, no Daphne, no new Celery task, no dependency on `MaterialRequest` gaining an ORDERED/DELIVERED lifecycle — the optional digest and that lifecycle work are both explicitly out of scope for this pass).

## Dependencies

- None blocking — this is additive to existing models (`ProjectPhase`, `Material`, `Expense`) and does not require the Channels/Daphne work gated in TODOS.md's "Railway WebSocket validation sprint" item, nor a `MaterialRequest` ORDERED/DELIVERED lifecycle that doesn't exist yet (see round-2 correction above).
